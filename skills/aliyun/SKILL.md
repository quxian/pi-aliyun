# Alibaba Cloud deployment

Use this package's deterministic CLI for OSS, FC, AliDNS and TLS. The CLI is `node <this skill directory>/scripts/cli.mjs`; it works from any project directory. Read [the package README](../../README.md) for installation, credential setup and configuration. The package has no dependency on the host application or a particular web framework.

## Installed platform

Start with `platform` to read the operator profile at `~/.config/pi-aliyun/platform.json`. If it is absent, use the standalone setup below. The profile has no credentials and is independent of any Agent host. Use `project-init --project pi-aliyun-<name>` to start projects in its persistent `projectRoot`; never put deployed source, configuration or certificate keys in a disposable conversation workspace or inside the package installation. Initialize a project Git repository and keep secrets ignored. Existing projects may be moved intact to `projectRoot` before deployment; update any old renewal registration.

An installed platform delegates project role initialization to a protected FC authorizer. Normal deployment can invoke it, but cannot change its code or pass its privileged role. The authorizer accepts only a project name and generates fixed trust/data policies for the approved shared instance. Do not generate administrator ZIP instructions for each new project. Within the installed scope, finish the project, get any new usage-cost approval once, record `db-approve`, then run `deploy`; the CLI handles the role, tables and publication. Treat a missing project role as planned initialization, not a request for manual RAM work. A permission failure after platform setup is a deployment defect to diagnose, not a reason to repeatedly ask the user to configure permissions. Do not silently broaden scope.

## Choose the project shape

- Generate static HTML/CSS/JS for OSS. A framework requiring a server for every page needs a static export or a different hosting plan.
- Run the backend as one ordinary HTTP server in one FC Web function, listening on `0.0.0.0` and the configured port. Keep business routes together. Code and dependencies must work on the selected FC Linux x86_64 runtime.
- Read [database choices](references/database.md) before designing persistence. Infer access patterns from the business: reuse suitable resources first; prefer CU-billed Tablestore SSD with zero reserved throughput for small online key/range workloads, HYBRID only for latency-tolerant workloads. SQL joins, ORM compatibility, cross-table transactions, financial balances or stock consistency can require RDS. Do not force these into a generic JSON row. FC local files are temporary.
- Use separate frontend/API subdomains under one AliDNS zone, in the configured account. Mainland OSS/FC domains require completed ICP filing. The CLI does not register domains, file ICP applications or change registrar nameservers.

## Work with the CLI

1. `init --config aliyun.json` writes the [configuration template](assets/aliyun.example.json) without overwriting a file. Adapt actual build commands, static output, backend code directory, runtime, account, region, resource names and domains. Omit frontend or backend if unused. No secret values belong in this file.
2. `doctor --config aliyun.json` checks local prerequisites without resolving credentials or calling cloud APIs. `plan` shows desired writes, not a live cloud diff. Review that the named resources are intended for this project. For persistence, add `database` and run `db-plan` plus read-only `db-inspect` to prepare concrete tables, a project runtime role, required deployment statements and a usage-based price estimate.
3. `build` runs the configured local build commands and checks upload artifacts without cloud mutations. It rejects symlinks and excludes credential-like files. Use a self-contained backend output directory; copy production dependencies there if they are not bundled.
4. Finish code, local checks and the concrete resource plan before asking for approval. If new charges, service terms or permissions are needed, ask ONCE with the business choice, named resources, monthly usage assumptions, recurring/purchase cost, network exposure, role trust/data scope and complete permission delta. Reuse explicit approvals within their scope. Do not ask the user to research products, invent credentials or choose details you can determine. An estimate is not a hard spending limit. Never authorize yourself by writing an approval file.
5. After user approval, record its exact fingerprint with `db-approve --fingerprint <db-plan fingerprint>`. The acknowledgement persists outside the package; changed plans require renewed approval. With the installed platform, `deploy` invokes the fixed-template authorizer when a project role needs initialization. Without a platform, an administrator uses `db-role` with a separately authorized identity and applies deployment statements without removing previous projects. The deployment role must not gain RAM policy-management rights. Platform installation is a one-time administrator operation; see the README.
6. When authorized, `deploy` builds, verifies the account through STS, verifies the runtime role, creates/checks database resources and injects connection metadata into FC, then publishes the application and certificate. Buckets and functions must be new or managed by this project. Unrelated resources or conflicting DNS records stop deployment. Failure may leave partial resources; fix its cause and rerun once rather than retrying indefinitely.
7. Verify HTTPS and a real API. For persistence, authenticate, write a unique disposable record, read it back, redeploy once and confirm it survives. Do not erase user records. Report actual results and unverified parts. Control-plane success alone does not prove the app works. Register new HTTPS projects with `schedule` when continuing an authorized renewal service.

For cross-project authorization, `policy` prints a concrete RAM policy for administrator review. It scopes OSS to `pi-aliyun-*-<accountId>` website buckets and DNS to the configured zone; FC/certificate operations remain account-wide. Standalone database additions are scoped to the configured instance and project's tables/role. The installed platform adds cross-project table management, project-role inspection/pass and invocation of the protected authorizer. It does not grant the deployment identity RAM administration. Each project needs distinct resources and domains. Do not claim that tags isolate one Agent's credentials from another's.

For HTTPS, use existing PEM files or the README's ACME DNS-01 configuration. OSS domain ownership verification is automatic: the CLI creates its own temporary `_dnsauth` TXT record when required and removes only that record. `renew` checks/renews and uploads certificates without rebuilding applications. When recurring execution is requested, run `schedule --config <absolute project config>` as the deployment service user. On Linux, an administrator installs the shared systemd timer once with `install-renewal --user <non-root service user> --registry <absolute registry path>`. Register later projects with `schedule`; `renew-all` continues through individual failures and reports an overall failure. Verify the service and next timer run. Keep project configurations, renewal registry and certificate/account key files outside package installations and upload directories. Do not promise failure notifications from the timer; it records service logs.

The HTTP trigger is anonymous at the cloud boundary and the default FC URL is disabled. Implement the application's authentication and authorization in its HTTP server. Do not put cloud keys in browser code; use FC's runtime role for cloud access. Deployment credentials follow the official SDK chain and are distinct from the application's environment.

Defaults scale FC to zero and cap its instance quota. Do not add keepalive requests, an always-running instance, NAT, Redis, API Gateway or a new database without a business need. Set sensible per-request timeouts; work that must outlive a response needs a proper asynchronous execution path.
