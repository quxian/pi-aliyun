# Alibaba Cloud deployment

Use `node <this skill directory>/scripts/cli.mjs` from the business project. The CLI manages static frontends on OSS, HTTP backends on FC, AliDNS/HTTPS and Tablestore. Existing SQL connections can use `backend.envFrom`; SQL provisioning and schema changes require product-specific work. Preserve the application's data semantics when choosing infrastructure.

When Client Pi supplies this package through Connections, the host account and credential source are already configured for all Agents. Run `account` to read deployment defaults and the user's recorded authorization; do not copy credentials into Agent settings or ask the user to configure each new Agent. Reauthorize in Client Pi → 连接 → 阿里云 only when the connection has expired. Missing website defaults do not mean the account is disconnected: choose an authorized DNS zone from the task or the connection's discovered domains when publishing a website, and supply `init --zone <zone>` if no default was saved. Never read or print the credential file named by `PI_ALIYUN_CONNECTION_FILE`; the CLI handles it internally.

`connection` returns safe identity metadata, discovered domains and read-only service checks; it accepts optional JSON on stdin with a `region`. Each check covers only its named read operation. `account-owner` identifies the main account's permission basis, not a successful deployment; `unverified` means RAM deployment rights cannot be fully simulated and does not disable the connection. A denied list operation need not imply denied writes. Do not request broad new rights merely to turn every read check green. FC uses ROS for deployment, inspection, renewal and deletion; its connection check is `ros:ListStacks`, not a direct FC request. Use the package commands instead of calling FC APIs with OAuth or asking for another credential type. Real operation failures identify the action that needs attention.

## Start from the user's request

When the user has established development-through-deployment as the workflow, a feature request includes implementation, deployment and acceptance. The user need not name this skill or repeat the cloud setup. Respect requests limited to discussion or local work. Choose routine technical details from the business needs and approved account defaults; ask only for missing decisions that materially affect the result or authorization. Carry the task through to a usable URL and report the verified outcome.

For an existing app, locate its persistent project and `aliyun.json` using the supplied path or retained project context before initializing anything. A new conversation or feature is not a new application. If the target is genuinely ambiguous, clarify which app rather than creating another resource set. Run the CLI on the configured deployment host as its service user; the browser's login state and the conversation workspace do not define cloud credentials or application ownership.

Read the relevant reference when needed: [account setup](../../README.md#配置账号) for missing configuration or credentials, [deployment configuration](../../README.md#开发和部署) for new or changed deployment settings, [database choices](references/database.md) when designing or changing persistence, and [HTTPS](../../README.md#域名和-https) for certificate setup or renewal. Routine updates can use the existing project and account configuration directly.

## Authorization and ownership

Read `account` once for this task unless already read in the current execution. Reuse its approved products, specifications, region, domains and spending scope across applications and conversations. Record or expand authorization only after actual approval. A new application name needs no new approval within that scope. Present any real expansion as one concrete cost and permission delta; available RAM rights alone do not authorize spending. If `authorization` is absent, use explicit approval in the current conversation or ask for the missing scope; profile defaults alone are not approval.

The saved region/domain are deployment defaults checked by this package, not RAM isolation boundaries. They do not narrow OAuth credentials or replace the user's approved scope. HTTPS may reuse supplied certificates or use ACME. ACME contact email is optional; record `acmeTermsAccepted` only after the user actually accepts the selected CA's terms, including when enabling HTTPS after connecting the account.

Create only resources the application needs. A static site needs no backend or database; a compute-only API needs no database or data-access role. Each required business resource belongs to its application and is reused for updates. Shared account settings, DNS zone, deployment identity and renewal service are account infrastructure, not shared business data. Share a database only for an explicitly requested data-sharing requirement; record its owner and concrete purpose in `database.shared`. Being part of one system or calling another service does not by itself require shared storage.

The deployment identity is a trusted management identity with RAM policy management rights; name prefixes are not a privilege-escalation boundary, and processes using that identity are not isolated. Never forward deployment credentials into application code, functions, frontend files or logs. Managed database applications receive a separate FC runtime role limited to their own or explicitly shared data.

## Develop and publish

1. Identify the application's frontend, API, authentication and persistence needs. For existing code, preserve its behavior and check how it fits the supported deployment shape before changing its architecture. Choose the lowest-cost database meeting actual queries and consistency requirements; omit it when unnecessary. FC local files are temporary.
2. For a new application, use `init --project pi-aliyun-<name>`. For existing source without deployment configuration, add `--config <project>/aliyun.json`. `init` creates configuration only: adapt its build paths, commands and runtime to the actual application. Defaults are starting values within the approved scope. Keep source, config and private files in a persistent project directory outside the package installation and temporary workspaces; use Git with secrets ignored. Reuse the configuration and stable resource names on updates.
3. Declare only needed components in `aliyun.json`. OSS serves public static files; FC runs an HTTP server listening on `0.0.0.0` and the configured port, with Linux x86_64 production dependencies. A backend needs a read-only, unauthenticated health endpoint returning 2xx without sensitive data. Set the frontend's API URL in the application/build configuration. For cross-origin frontend/API access, implement CORS and OPTIONS in the backend for the exact frontend origin and required headers/methods; ROS custom domains do not expose CORS configuration. Verify it as part of the application, without asking the user to configure the cloud console. Enforce business authorization before protected data access; CORS is not authentication. For Tablestore, use fresh FC runtime credentials as described in the database reference.
4. Run relevant local checks. Review `doctor` and `plan` for new or changed deployment configuration, and `db-plan` for changed database usage assumptions. These commands do not simulate live permissions. `deploy` builds, checks the account, prepares declared resources and runtime permissions, publishes code and configures DNS/HTTPS; separate `build`, `db-setup` or `schedule` calls are unnecessary in the normal deployment path.
5. Require the built-in HTTPS and configured backend health checks to pass, then verify the relevant business flow, including frontend-to-API access when present. On first delivery or a persistence/deployment change, verify authenticated write/read and data survival across one redeploy when persistence is used. Use disposable records and preserve user data. Routine updates need only affected checks. For multiple independent apps, check distinct resource ownership and runtime data scope. Retain the project/config location and URLs in the host's normal project context so later work finds the same app; report what was actually verified.

Backend code is uploaded automatically to an application-owned private OSS bucket. ROS manages its FC function, instance cap, trigger and HTTPS domain; no separate ROS setup is needed. `status` reports ROS deployment state; `verify` checks live HTTPS. Do not modify managed FC resources outside this stack or adopt pre-existing functions.

Use low resource specifications within the approved scope, with zero minimum FC instances and a small instance cap. Add paid components only for an actual need. An instance cap does not limit cumulative spending.

Use `backend.envFrom` for business secrets. It reads deployment process variables, not `.env` files automatically. Persist application-owned secrets in an ignored private file (0600) outside build output, and load it on each deployment, for example `node --env-file=<private-file> <skill-directory>/scripts/cli.mjs deploy --config <config>`. Reuse existing secrets during ordinary updates. Keep their values out of chat, logs and frontend bundles; missing variables are a loading problem to investigate, not a reason to rotate credentials.

## Inspect, maintain or remove

For cloud state use `status`; for local/cloud/HTTPS problems use `diagnose`; to rerun network acceptance use `verify`. `doctor` is a local check: absent credential environment variables do not mean credentials are unavailable, since the SDK can use the service user's credential file or host role. Do not ask for new keys until actual credential resolution has failed and existing configuration has been checked. Never request secret keys in chat.

Unknown ownership or conflicting DNS stops deployment. Inspect the error and partial completion, fix the cause, and retry with the same project/config. Keep the resource manifest; deleting it, renaming the app or recreating its database does not repair a failed deployment. Missing permissions within the approved scope are account setup defects: prepare the specific policy correction, apply it if the current identity permits, or request only the required administrator action under the existing approval. Do not broaden rights or repeat the application's spending approval. Upload success alone is not deployment acceptance.

Use `renew` for certificates without rebuilding. Configured ACME projects register for renewal during deployment; Client Pi checks registered certificates automatically while it is running on either a local computer or server. Do not ask its user to install a timer. For standalone CLI hosts, install the documented renewal timer once and retain its service identity, registry and private keys. Reuse the user's approved CA terms. See the HTTPS reference when setting up this facility or resolving certificate issues.

When the user explicitly requests deleting an application and its data, follow [deletion](../../README.md#查看排障与删除): preview with `destroy --config <path>`, then execute with `--confirm <exact-project-name>`. No repeated account approval is needed. Deletion permanently removes owned cloud data without automatic backup; shared dependencies and ownership blockers must be resolved first. Keep the project and resource manifest until completion, retry partial failures with the same command, and report retained local files or unowned certificates. Do not broaden deletion to unrelated resources or use real user data to test deletion.
